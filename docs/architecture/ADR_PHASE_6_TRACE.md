# ADR: Phase 6 (v2.5 Trace) implemented backward causal-chain tracing as another projection, with zero new graph systems

**Status:** Accepted. Implemented in `src/lib/public/trace-projection.ts`, an extension to `EvidenceGraph`, and one integration point (Work detail pages).

**Context:** the HubZero Public v2.5 Engineering Architecture plan scoped Phase 6 as the first capability built on top of the Evidence Graph platform (Phases 3–5): Trace, letting a reader follow a connected chain of evidence across published records. `ADR_PHASE_1_DEFERRALS.md` had already anticipated this — it deferred a `chain.ts` layout module specifically "until Phase 6 (Trace)… so the layout function's shape is validated against real traced paths from the first commit rather than a hypothetical one." This phase is that validation, and the answer it produced is more specific than the original guess: a `chain.ts` module was not needed at all.

## Audit: what already existed

- **`entity-graph/query.ts`** — `GraphQuery.outbound`/`inbound` already provide one-hop traversal from any entity. Nothing needed to change here; a multi-hop walk is orchestration on top of these, not a new primitive (this matches the exact prediction in the `hubzero-entity-graph-and-test-stack` project memory: "Multi-hop traversal… is straightforward to build by walking `query.outbound`/`inbound` repeatedly — the hard part (the indexed graph itself) already exists").
- **`evidence-projection.ts`** — `projectEvidence` is one-hop only (a subject plus its direct connections), by design (Phase 3 confirmed this is the correct, unmodified shape for the fan use case). Its two internal helpers, `labelFor` (directional relationship labeling) and `refKey` (entity identity key), were exactly what a multi-hop walk also needs at every step — exported for reuse rather than reimplemented.
- **`graph-layout/layered.ts`** — the audit's key finding. `layoutGraph` performs a BFS-from-root layering: each node lands in the layer equal to its graph distance from `rootId`. For a **path** graph (each node connected to exactly one predecessor and one successor) this produces exactly one node per layer — a straight left-to-right sequence — with no changes to the algorithm at all. The "layered" name describes what it computes (nodes assigned to depth layers), not an assumption that layers must be wide (fan-shaped); a chain is simply the graph shape where every layer happens to be one node deep. Confirmed by test: feeding `layoutGraph` a path-shaped `GraphLayoutInput` produces monotonically increasing node x-coordinates with zero vertical stacking, i.e., a chain, using the exact same function Engineering Profiles' and Homepage's fan diagrams already call.
- **`EvidenceGraph.tsx`** — before this phase, its props (`subject`, `relationships`) and internal layout-input construction assumed exactly one shape: every relationship as an edge from `subject`. This was the one real gap: the component's public API, not the layout it calls, needed to support a second edge-wiring shape.
- **`EvidenceGraphFocusSync.tsx`** — already fully generic (pairs any two elements sharing a `data-evidence-node` value); nothing to change.

**Conclusion, directly answering the audit's own questions:** chain layout is not "required" in the sense of needing new math — it already existed as a special case of the layered algorithm. What was missing was entirely at the `EvidenceGraph` component boundary (how the input graph gets built from props) and at the projection boundary (a function that walks multiple hops and returns an ordered path instead of a one-hop fan).

## Design: `EvidenceGraph` gained one prop, not a second component

`EvidenceGraph` gained `layout?: 'fan' | 'chain'`, defaulting to `'fan'` — the exact behavior every existing caller already gets, verified by a test asserting the markup is byte-for-byte identical whether `layout` is omitted or passed explicitly as `'fan'`. The two modes differ in exactly one place: how each edge's `source` is computed (`'subject'` for every edge in fan mode; the previous hop's node id for `order > 0` in chain mode). Layout invocation (`layoutGraph`), the SVG structure, the two node-rendering styles (a bold root label; a smaller edge-label-plus-title for every other node), and the `data-evidence-node` tagging are all one shared code path for both modes — there is still exactly one graph renderer, per the brief's explicit requirement. `TraceGraph`/`ChainGraph`/any page-specific rendering component was not created.

The one internal rename (`GraphEntity`'s `'subject' | 'relationship'` union became `'root' | 'leaf'`) reflects that a chain's later nodes aren't structurally different from a fan's leaves — both are "a node reached by one incoming relationship, rendered with an edge label above its own title." Trace didn't need a third visual style; every non-root position in a chain reuses the fan's existing leaf styling untouched.

## The projection: `trace-projection.ts`

`projectTrace(query, destinations, subjectRef, options)` walks a single path outward from `subjectRef` one hop at a time, entirely on top of the existing `GraphQuery.outbound`/`inbound`. Design decisions:

- **Direction defaults to `'inbound'` (backward).** `ADR_PHASE_1_DEFERRALS.md` named the feature "Trace's backward-causation path rendering," and the domain's two real lineage kinds (`labGraduatedToBuild`, `buildAppliedInWork`) are both stored forward (Lab → Build, Build → Work) — walking backward from a later-stage record (a Work item) reads as "what produced this," the more natural narrative than walking forward from an arbitrary Lab. `direction: 'outbound'` is supported and tested for a future forward-tracing caller, but backward is the default because it's the framing the plan actually named.
- **`kinds` defaults to `['graduated_into', 'applied_in']`** — the two graph-level kinds `normalizeRelationshipAssertions` already guarantees are 1:1 per entity (its own conflict-resolution logic removes competing `labGraduatedToBuild` edges before the graph is ever built, so a chain never has to choose between candidates at that hop). Deliberately excludes `related_to` (lateral, not causal — tested: a `workRelatedLab` edge produces zero trace steps) and `uses` (a Blueprint reference is not a 1:1 predecessor/successor step; a Build can use several Blueprints, which isn't a single path). Both are overridable via `options.kinds` for a future caller with a different, equally well-defined causal chain to walk.
- **Visibility fails closed**, exactly like `projectEvidence`: the chain stops the moment a hop's destination isn't in `destinations`, rather than skipping the gap and continuing past it. `disclosure` reports this the same shape `EvidenceProjection.disclosure` already does (`{total, visible, hidden}`), so a truncated chain is diagnosable the same way a partially-hidden fan already is.
- **Cycle guard and `maxHops` (default 6)** bound worst-case traversal — defensive, since the lineage data itself shouldn't cycle, but a dependency-free traversal shouldn't trust that from the data alone.

Each step's shape is `PublicRelationship` — the exact type `EvidenceProjection.relationships` already uses — not a new type. This is what let the rest of the implementation stay this small: a chain step and a one-hop relationship are, to every consumer downstream of the projection, the same kind of fact.

## Integration: Work detail pages, backward through Build to Lab

`PublicEntityDetail`'s Work variant gained one new required field, `trace: PublicRelationship[]` (empty array when there's no lineage to trace, matching the existing `gallery`/`documents` convention of always-present arrays rather than optional fields). `repository.ts` gained `resolveTrace`, a direct parallel to the existing `resolveRelations`, called once in `findDetail`'s `work` case using the same `EvidenceContext` `relationships` already resolves from — zero new queries.

`PublicCollectionDetail.tsx` renders a new section when `entity.type === 'work' && entity.trace.length`: `EvidenceGraph` in `'chain'` mode as `RelatedRecordsSection`'s `headerContent`, the ordered steps as `RelatedRecordsSection`'s flat-mode relationship list, both wrapped in `EvidenceGraphFocusSync` — the identical composition pattern Phases 3–5 already established for the fan case, not a new one invented for Trace. It sits beside the existing one-hop "Product lineage" section (which never fires for Work today — `labGraduatedToBuild` never directly involves a Work record — so this is a purely additive section, not a replacement of anything).

**Scope decision:** this phase wires Trace into exactly one detail type (Work, backward). Lab (forward: what this investigation eventually shipped and where it was applied) and Build (bidirectional) are natural, low-risk follow-ups — `resolveTrace`/`projectTrace` already support both directions — deliberately left for a future phase to keep this one's diff focused, the same scoping discipline Phases 2, 4, and 5 each applied to their own adoption surface.

## Performance

- **Traversal cost:** bounded by `maxHops` (6) and, in practice, by the domain having exactly two lineage kinds — no realistic chain approaches that bound. Each hop is an O(1) map lookup (`GraphQuery`'s prebuilt indexes) plus a small array filter/sort over a single entity's connections, not a graph-wide scan.
- **Query cost:** zero new database queries — `resolveTrace` reuses the same `EvidenceContext` (`query`, `destinations`) already built once per request for `relationships`.
- **Rendering cost:** identical SVG complexity class to fan mode — one `<g>`/`<circle>`/two `<text>` per node, one `<polyline>` per edge — bounded by the same small `maxHops`-capped step count.
- **Hydration/bundle:** zero new client components. `EvidenceGraphFocusSync` is reused, not duplicated; `EvidenceGraph` remains a Server Component in both modes.
- **Homepage/Engineering Profiles:** untouched by this phase, so neither can regress from it — verified by the full existing test suite passing unchanged.

## Accessibility

Unchanged model from Phase 3: the SVG stays `aria-hidden` with an equivalent text summary (now describing an ordered path — `"Trace: A → B → C."` — rather than a fan's "connects to" list, since the two structures mean different things and a screen reader summary should say so). The accessible, keyboard-operable path is the plain `<a>` tags `RelationshipCard` already renders inside `RelatedRecordsSection`'s reused flat-mode list — no second focus model, no `tabIndex` added anywhere, in either graph mode. One accepted trade-off: `RelatedRecordsSection`'s flat mode renders a plain `<div>` of cards rather than a semantic `<ol>`, so a chain's sequence isn't doubly reinforced by list semantics — DOM order (which assistive tech still reads in sequence) and each step's own directional label ("Informed by…", "Originated in…") together still make the causal order unambiguous in text, and reusing the primitive unmodified was judged the better trade than special-casing it for one caller. Reduced motion needed no new handling — no animation was introduced this phase, and the existing global `prefers-reduced-motion` rule already covers everything Trace's markup can trigger.

## Self-review

- **Did Trace reuse the platform, or create another graph system?** Reused it — zero new traversal primitives, zero new layout algorithms, one new optional prop on the one existing renderer, one new projection function shaped like the existing one, `EvidenceGraphFocusSync` reused verbatim.
- **Can Homepage continue unchanged? Can Engineering Profiles continue unchanged?** Yes to both — neither file was touched this phase, and `EvidenceGraph`'s default-`'fan'` behavior is proven byte-identical to before.
- **Did we preserve backward compatibility?** Yes, proven by test, not just by inspection.
- **Would another future graph mode reuse this implementation?** The fan/chain split establishes the pattern a third mode would follow: a new edge-wiring strategy behind a new `layout` value, sharing the same render loop — not a new component.
- **Did we accidentally introduce page-specific logic into the platform?** No — `EvidenceGraph`, `graph-layout`, `entity-graph`, and `evidence-projection.ts` carry no Work- or Trace-specific knowledge. Everything Work-specific lives in `trace-projection.ts` (a public-domain projection, the same layer `evidence-projection.ts` already occupies) and in `repository.ts`/`PublicCollectionDetail.tsx` (the same composition layer `resolveRelations`/Homepage's evidence sections already occupy).
