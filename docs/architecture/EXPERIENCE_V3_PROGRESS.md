# Experience v3 — Progress Log

This is the canonical, in-repo record of what Experience v3 has actually shipped, milestone by milestone. It exists so a contributor — human or AI — with zero memory of prior sessions can read the repository and know the current stage, instead of relying on conversation history that doesn't persist.

**How to keep this current:** when a milestone completes, append a new `## Milestone N` section below in the same shape (What shipped / Why / Verified / Deferred). Do not rewrite prior entries except to correct a factual error — this is a log, not a living spec. If a milestone's decision is architecturally significant enough to need its own detailed rationale (the way v2.5's phases got individual `ADR_PHASE_N_*.md` files), write that ADR and link it from this entry instead of inlining it here.

**Branch:** `experience/v3`. As of Milestone 5, all work below is uncommitted in the working tree (`git status --short` shows the modified/new files directly — this log explains the *why* behind that diff, it doesn't replace reading it).

## Milestone 1 — Publishing Integrity

**What shipped:** Editing an already-`published` entry now requires `publish` capability (Admin/Head Admin only, via `requireEntryCapability`/`canEditEntry` in `lib/auth/permissions.ts`) and is forced back to `inReview` on save, clearing any stale `reviewNote`. Added a `reviewNote` field to the shared `PublishableEntity` model. Added a real reviewer **reject** path (`inReview → draft`) requiring a non-empty note, gated by `approve` capability (`canReject` in `lib/studio/workflow-permissions.ts`), surfaced as a Reject button + inline note field in `StatusStepper`.

**Why:** A prior repository audit found a published entry could be silently rewritten by its owner or any Admin with zero re-review gate, despite design docs claiming this gap was closed. This closed it for real, in code.

**Verified:** Typecheck/lint clean; 8 new tests directly covering `canEditEntry`/`canReject`. Not covered: full server-action integration tests (no `next/navigation`/`next/cache` mocking infra exists in this repo yet) and live Studio login flow (this repo's local `.env.local` points at a real database, so no test credentials were fabricated against it — see `docs/operations/ENGINEERING_BOOTSTRAP.md`'s working assumptions).

**Deferred:** No draft/live dual-copy versioning (an edited published entry disappears from public view until re-approved — a deliberate, stated trade-off, not a bug).

## Milestone 2 — Preview Integrity

**What shipped:** Real full-page preview via Next.js Draft Mode. `/api/preview` (enable — requires a real Studio session + `canActOnEntry`) and `/api/preview/exit` (disable). `lib/public/repository.ts`'s `findDetail`/`visible`/`mapSummary` gained a `bypassStatus`/`options.preview` path that bypasses only the *subject* entity's status gate — never propagated into relation/trace resolution. `lib/public/queries.ts` skips `unstable_cache` when previewing. A site-wide `PreviewBanner` renders whenever Draft Mode is active. The old in-Studio `BlockEditor` preview toggle (which rendered `BlockRenderer` — a Studio-only component — against unsaved in-memory blocks, and had falsely claimed to be "the same component tree" as the public site) is gone; its toolbar button now flushes autosave and opens the real Draft-Mode URL.

**Why:** `BlockRenderer` (Studio admin chrome) and `ProseRenderer` (public `.public-*` CSS) are, and always were, genuinely separate renderers. The old toggle's "what I see is what ships" guarantee was false. Draft Mode makes the guarantee true by construction — it's the same render path, not a resemblance of it.

**Verified:** Typecheck/lint clean; 429/429 tests passing (4 new tests for the bypass logic). Live-verified: real public pages unaffected, `/api/preview` correctly 401s unauthenticated. Not verified live: the full authenticated enable→preview→approve flow (same test-credential constraint as Milestone 1).

**Deferred:** `BlockRenderer`/`ProseRenderer` stay two separate components by deliberate architectural decision — see `PLANNING.md` §18/§26's Experience-v3 update notes. Not a gap; don't propose merging them without re-opening that decision explicitly.

## Milestone 11 — Content Security Policy Validation

**What shipped:** Milestone 10's newly-added CSP (`script-src 'self'`, no exception) turned out to block Next.js App Router's own inline hydration scripts — confirmed live in a real browser before touching any code: a blank page and repeated `Error: Connection closed` exceptions from the React Server Components stream reader, the signature of `self.__next_f.push(...)`'s inline script calls being silently dropped by the browser. Investigated and tried the officially-documented, stricter fix first — a per-request nonce plus `'strict-dynamic'`, generated in `src/middleware.ts` and threaded through automatically by Next.js (confirmed by diffing the CSP header's nonce against the HTML's `nonce="..."` attributes — identical, with no explicit `headers()` call needed anywhere). It worked perfectly in `next dev` and for genuinely dynamic routes. It failed, empirically, for this app's statically-generated/ISR routes under `next start`: a page pre-rendered once at build/revalidation time ships with no nonce baked into its scripts at all (no request, no middleware, ever touches that render), while middleware still stamps a fresh, different nonce onto every subsequent request's CSP header — reproducing the identical blank-page failure, now scoped to every cached page instead of every page. Confirmed live via `x-nextjs-cache: HIT` on the broken response. Concluded that forcing full dynamic rendering site-wide to make the nonce match would be a disproportionate trade against the `revalidate = 86_400` ISR architecture two prior milestones (5 and 8) already verified as deliberate and correct, and reverted to the simpler, working answer: `'unsafe-inline'` for `script-src` (and, unchanged from Milestone 10, `style-src`), with every other directive kept at `default-src 'self'`-level strictness. `src/middleware.ts` was reverted to its original Studio-only scope in the process.

**Why:** A CSP that breaks the application it protects isn't a stricter policy, it's a broken one — and this project's own established discipline (verify empirically, don't trust the first thing that compiles) applied exactly here: the nonce approach *looked* correct, passed every dev-mode check, and only failed under a specific, easy-to-miss combination (production + a statically-cached route) that a dev-only verification pass would never surface.

**Verified:** `tsc --noEmit` 0 errors, lint clean, 446/446 tests unchanged, production build succeeds with all ISR `revalidate`/`expire` windows intact (confirmed directly from the build's route table, not assumed). Live-verified in both `next dev` and `next start` across every major public route plus Studio (authenticated and unauthenticated) — zero console errors on any, including real interactivity (search palette with live results, Contact form field entry) and the specific previously-broken cached-page scenario. One real regression caught and reverted before it could ship: the broadened middleware matcher tried during the nonce attempt made Auth.js set its CSRF/callback-url cookies on anonymous public page views, directly contradicting `/privacy`'s claim that a cookie is set only on Studio sign-in — confirmed via `curl` before and after the fix.

**Deferred:** `script-src`/`style-src`'s `'unsafe-inline'` is a disclosed, real reduction from the theoretical maximum, not a zero-risk default — compensating controls (DOMPurify sanitization of all authored rich-text content, Zod validation on every form input, Origin-header CSRF protection native to Next.js Server Actions) exist independently of CSP. Revisiting nonce-based CSP would require either abandoning this app's ISR architecture or Next.js's (currently experimental) Partial Prerendering maturing enough to reconcile static shells with per-request nonces — neither is in scope for a CSP-correctness milestone. No CSP-violation-reporting endpoint (`report-uri`/`report-to`) is configured, so a future regression here would only surface via manual testing, not telemetry.

## Milestone 12 — Editor State Management (v3.1 Phase 1)

**What shipped:** A platform-level editor-state layer (`src/lib/studio/editor-state/`) plus its shell components (`src/components/studio/editor/`), adopted by every editable Studio surface at once rather than per collection. Its core is `EditorHandle` — one interface describing "an editor that can hold unsaved work" — and `EditorRegistry`, a plain external store (subscribe/`getSnapshot`, read through `useSyncExternalStore`) that owns the whole navigation decision table: nothing dirty → go; only autosaving editors dirty → flush silently, then go; anything else → ask. Dirty state is derived by serializing what a form *would submit* (`serializeFormEntries` over `FormData`) and diffing it against the last snapshot actually saved, so editing a value and putting it back reads as clean, and so a field type added later is covered with no new code — which works precisely because the Studio already had one form convention (uncontrolled inputs + real hidden inputs for media/relation/timeline fields) rather than a form-state library. `useFormEditorState` wires that to a save lifecycle, in-place discard (a keyed remount of the field subtree, not a page reload), and `Ctrl/Cmd+S`; `EditorForm` is the wrapper a collection form is now written inside, so a form file contains only its fields. Thirteen editors adopted it: Work, Builds, Blueprints, Labs, Notes, Careers, Engineering Profiles, Services, Team, Users, Taxonomy, Studio Settings, own-Profile — plus Lead notes, which is not a content collection but is an editor. `EditorGuardProvider` (wrapping `StudioShell` in the `(shell)` layout) guards departures at three levels: a capture-phase `document` click listener for every anchor, a same-URL history sentinel plus `popstate` for Back/Forward, and `beforeunload` for refresh/tab-close — registered only while work is at risk. Programmatic navigation has no DOM event to intercept and opts in explicitly through `useGuardedRouter` (command palette, `g`-chord jumps). The Document Engine registered too, as `savesAutomatically: true, showsSaveBar: false`: it keeps its own header controls but can no longer be left with a failed or mid-debounce autosave, and `useAutosave.saveNow()` now returns a real success boolean so the guard decides on fact rather than on "didn't error".

Two behavioral changes were required and are deliberate. Every metadata **update** action now returns `{ ok: true }` instead of `redirect`ing to the detail view (`createEntryUpdateAction` and the bespoke Service/Team/User/Taxonomy/Settings/Profile/Lead-notes equivalents; `revalidatePath` is unchanged, and every **create** action still redirects). A "✓ Saved" state is only observable if the page that saved is still on screen, and leaving is now an explicit choice ("Save & Leave"), not a side effect of saving. Second, `EditorForm` dispatches its action from `onSubmit` inside `startTransition` rather than via `<form action={fn}>`: React 19 calls `requestFormReset` on every action passed to the `action` prop, which was invisible while saves redirected but would snap every field back to its pre-save `defaultValue` on a form that stays put. Native constraint validation is unaffected, since a browser only fires `submit` on a valid form. The one cost is that Studio metadata forms no longer submit with JavaScript disabled — a theoretical loss for an authenticated CMS whose media picker, command palette, relation pickers, and block editor were already JS-only.

**Why:** These behaviors are a property of "being a Studio editor," not of being a Work entry — implementing them eleven times would have guaranteed eleven slightly different answers to "what does Saved mean," and is exactly the class of duplication Milestone 5 existed to undo. Deriving dirty state from the form rather than from per-field wiring is what makes the promise "a future editor opts in with minimal code" true rather than aspirational. The layer is also deliberately shaped to accept autosave, presence, conflict resolution, and version history later without redesign — `save()` returns `Promise<boolean>` so a future conflict check can refuse; editors carry stable `id`/`label`; and `savesAutomatically` already distinguishes autosaving from manual editors without the shell naming the Document Engine — but none of those are implemented here.

**Verified:** `tsc --noEmit` 0 errors, lint clean, 484/484 tests passing (21 new: dirty-detection semantics and the full navigation decision table, both as plain TypeScript with no DOM), production build succeeds with the Studio route table intact. One pre-existing test (`StudioSettingsForm.test.tsx`) needed a `next/navigation` stub, since every Studio form now transitively depends on the App Router.

**Deferred / not verified:** The browser-side half — anchor interception, the history sentinel, `beforeunload`, the dialog and sticky bar — was **not** exercised live. Every Studio route is auth-gated, and this repository's own operating rule (`docs/operations/ENGINEERING_BOOTSTRAP.md` §3) forbids fabricating credentials against the configured database, which `.env.local` may point at production. `/studio/login` compiling and rendering, and `/studio/*` redirecting, is the extent of the live check. Interactive verification of the thirteen editors against the phase brief's own test list (edit, save, discard, Save & Leave, sidebar, Back, refresh, Ctrl/Cmd+S, validation and save failures) is the outstanding item and needs a real session. Two known gaps, both narrow: signing out from the user menu is a form submission rather than an anchor, so it is not intercepted; and the guard's history sentinel truncates forward history while an editor is dirty, an accepted cost of absorbing Back without letting the route change first. Autosave, collaborative editing, offline editing, conflict resolution, version history, and live presence remain unimplemented by design — the phase brief asked only that they not be designed out.

## Milestone 13 — Editor State Stabilization (v3.1 Phase 1, hardening pass)

**What shipped:** Six corrections to Milestone 12's editor-state layer, found by a critical architecture review and then confirmed — or, in one case, discovered — in a real authenticated browser session.

1. **Concurrent-save deadlock (critical).** `useFormEditorState.save()` stored a single promise resolver, so a second caller overwrote the first's and stranded that promise forever. Because "Save & Leave" awaits exactly such a promise, `Ctrl/Cmd+S` pressed during a save could leave the leave-dialog waiting on a result that would never arrive — with every button disabled, which made it a hard trap. `save()` now coalesces concurrent callers onto one in-flight promise, and every exit path (action result, a `requestSubmit` that produced no submit event, unmount) settles it through one `settleSave` helper.
2. **"Stay Editing" is never disabled.** Returning to your own page is now unconditionally available, including mid-save. A `resolutionId` token means a save that lands *after* the author cancelled completes normally but no longer carries out the navigation they just called off.
3. **`useTransition().isPending` replaces the hand-rolled `refreshing` flag.** The old flag was set on the line after `router.refresh()`, so whether it actually tracked the refresh depended on React internals rather than on anything the code stated — and `canDiscard`'s "never restores a stale snapshot" guarantee rested on it.
4. **Navigation hardening.** `requestNavigation` now ignores further requests while a question is already open, so holding Back can't replace a pending intent whose `history.go(-2)` was built for a different stack. The history sentinel's lifecycle is read from `history.state` instead of mirrored in a React ref, making push and pop idempotent and self-correcting against the real stack.
5. **Dirty-state recomputation throttled** to a 120ms window with a leading edge, so the first "Unsaved changes" is never delayed. Measured rather than assumed (see below).
6. **The invariant is documented.** [`ADR_EDITOR_STATE.md`](ADR_EDITOR_STATE.md), indexed in `docs/README.md` and pointed at from `EditorForm`'s own doc comment, states the native-form-control requirement, what silently breaks without it, why it is a convention rather than an enforced rule, and the one-second check that catches the whole failure class.

**One real bug found only in the browser:** with the command palette open, a guarded navigation mounted the leave dialog *underneath* Radix's modal stack — `aria-hidden="true"`, behind the palette's focus trap — leaving the author with an unreadable, unclickable dialog and a palette that never closed. Root cause: `CommandPalette.navigateTo` called the guarded push synchronously, before React had committed the palette's own close. Fixed by deferring the push one task. Any future surface that navigates from inside its own modal must do the same; the fix carries that note.

**Why:** These are the failure modes that decide whether an editor-state layer is trustworthy. A guard that can trap an author in a modal is worse than no guard, and a `canDiscard` gate that only appears to work is worse than one that visibly doesn't.

**Verified:** `tsc --noEmit` 0 errors, lint clean, 488/488 tests (4 new, covering intent-replacement, cancel-during-save on both the manual and silent-flush paths, and re-arming after resolution), production build succeeds with all 77 static pages generated.

Live-verified against a real authenticated Studio session on the production database, deliberately restricted to flows that perform **no writes** — every check below left the database untouched, confirmed afterwards by reloading and by the Work list still reading "Published / 2 weeks ago":
- **Blueprint editor (full):** edit → dirty; revert to the original value → clean (the brief's own §2 example, exactly); sticky bar appears and disappears with dirty state; Discard restores in place without a reload; sidebar click → dialog, navigation blocked; Stay Editing → dialog closes, edit intact, still on page; breadcrumb click → dialog; browser Back → absorbed, dialog shown, sentinel re-pushed with Next.js's own `__NA`/`__PRIVATE_NEXTJS_INTERNALS_TREE` state preserved; **three consecutive Backs with the dialog open → still on page, `history.length` unchanged, no sentinel accumulation, original intent retained**; Discard Changes → navigates to the correct destination; command palette navigation → guarded (and, after the fix, the leave dialog is the active modal and hit-tests as clickable).

**Deferred / not verified:** Every flow that requires an actual write — successful save, "Save & Leave" through to completion, a failed Server Action, and repeated `Ctrl/Cmd+S` *during* a save — is **untested**, because `.env.local` points at `hubzero-prod` and `createEntryUpdateAction` demotes a published entry to `inReview`, so a test save on live content would unpublish it. These need either an explicit go-ahead on a draft entry or a scratch database. The concurrent-save fix in (1) is covered by unit tests but has not been exercised end-to-end in a browser, which is the gap that matters most. Also unverified: what Next.js's App Router does internally when it receives a `popstate` for an identical routing tree (a wasted RSC fetch or scroll reset would not have shown up in these checks). Known-narrow gaps carried forward unchanged: sign-out is a form submission rather than an anchor and is not intercepted; the sentinel truncates forward history while dirty; `Ctrl/Cmd+S` is global rather than scoped to an active editor, so a page with two `EditorForm`s would save only the first-registered one (no such page exists today); and unmounting an editor (the Document Engine's role tabs) still discards a pending autosave without asking.

## Milestone 14 — Navigation Guard Correctness (v3.1 Phase 1, final)

**What shipped:** One fix for one release-blocking regression that Milestone 13's own verification introduced and then caught.

The guard was deciding from *published* dirty state. Milestone 13 throttled dirty recomputation to 120ms, and the leading edge was consumed by the `click` that focuses a field — so the keystrokes that followed only scheduled the trailing run. A navigation click landing inside that window was judged against dirty state computed *before* the author typed, and was let through. Reproduced deterministically: type a character, immediately click a sidebar link → navigated away, no dialog, edit gone. The same sequence with a two-second pause prompted every time.

Two changes, both inside the existing architecture:

1. **`EditorHandle.isDirtyNow?()`** — an optional, synchronous live probe. `EditorRegistry.dirtyEditors()` now routes every safety decision through it, falling back to the published flag for editors that don't offer one (the Document Engine, whose dirty state is already a reference comparison evaluated during render). A probe that throws is read as dirty, never as safe to discard. `useFormEditorState` implements it by re-serializing the form and comparing against the saved baseline at call time — one `FormData` walk (~0.2ms on the largest Studio form), paid only when someone tries to leave, never per keystroke.
2. **The clean → dirty edge is no longer throttled.** Throttling now applies only once the editor is already dirty — which is also where the cost actually is, since sustained typing spends all its time in that state. This closes the same lag for the `beforeunload` registration and the save bar, which are driven by published state rather than by the probe.

The throttle is retained; its measured benefit (11.4ms/s → 1.6ms/s of work during sustained typing on the largest form) is untouched. What changed is that it now governs only what is *rendered*. Throttling what is *decided* was the bug.

**Why:** The two questions have different tolerances. "What should the save bar show?" can lag a frame. "May this navigation proceed?" cannot lag at all — the gap is exactly wide enough for ordinary typing-then-clicking to fall through, and the failure is silent data loss, which is the one outcome this entire phase exists to prevent.

**Verified:** `tsc --noEmit` 0 errors, lint clean, 492/492 tests (4 new: stale-clean flag with a dirty probe still blocks; stale-dirty flag with a clean probe does not prompt; a throwing probe blocks; no-probe editors fall back).

Live-verified in a real authenticated Studio session. The race — type one character, then immediately trigger navigation — now prompts on **all four vectors**: sidebar link, breadcrumb, browser Back, and command palette (verified with the leave dialog active and hit-testable, not suppressed behind the palette). Edit → revert to the original value → dirty clears, bar disappears, chip returns to "Saved". Write flows re-verified end to end against a throwaway draft (`HZ-BP-012`, created and deleted within the pass): create-and-redirect; `Ctrl/Cmd+S` save (1 POST + 1 refresh, "Saved at 5:07:53 PM", stays on page); **concurrent save — Save & Leave with 12 `Ctrl/Cmd+S` presses during the in-flight save produced exactly 1 POST, 1 refresh, and exactly 1 navigation to the correct destination**; failed save (server-side Zod rejection → error banner, field error, "⚠ Save failed", dirty preserved, snapshot unchanged, no navigation). Blueprints collection back to 10 records, zero `zztest` documents remaining; the published Blueprint used for the race tests was never saved.

**Deferred / not verified:** Synthetic DOM events dispatched from the automation harness gave inconsistent results and were abandoned in favour of real user input — so the race is verified at real-input timing (tens of milliseconds), not at same-tick timing. `alt+Left` is not delivered to the page by the automation, so browser Back was exercised through a real `history.back()` traversal rather than the keyboard shortcut. Known-narrow gaps carried forward unchanged: sign-out is a form submission rather than an anchor and is not intercepted; the sentinel truncates forward history while dirty; `Ctrl/Cmd+S` is global rather than scoped to an active editor; unmounting the Document Engine's role tabs still discards a pending autosave without asking.

## Milestone 15 — Featured Order System (v3.1 Milestone 2)

**What shipped:** A first-class editorial ordering system for the five content collections the homepage ranks — Work, Builds, Blueprints, Labs, Notes — replacing two separate implicit mechanisms with one explicit one.

**Data model.** Each of the five gains `featuredOrder: number | null` (`null` = not featured, positive integer = featured, lower first). The boolean `featured` flag is gone from all four collections that had it; Work never had one at all, so its homepage slot was previously chosen for it. `Service` keeps its own unrelated `order` field and `featured` boolean — a different contract on a shipped surface, deliberately untouched.

**The ordering model is an ordered array, not a stored position.** `lib/studio/featured-order.ts` treats the featured set as one list of ids and derives positions from array index at the moment of persistence. Canonical numbering (`1..N`, dense, unique) is therefore not a rule enforced after each mutation — it is the only state the system can express. There is no code path that can produce `1, 3, 9, 14`, because position is never stored independently of order. `createFeaturedOrdering` (`lib/db/featured-ordering.ts`) writes whole-set for the same reason: clear everything currently featured, then assign `1..N`. That also makes the write idempotent, so a retried save cannot compound.

**Repository / API.** One shared factory mixed into all five repositories gives each `listFeatured()` and `setFeaturedOrder()`. `selectFeatured()` is the single place ordering is applied — Studio and public surfaces both read through it, so "lower number first" is stated once and no UI sorts for itself. It also tolerates non-canonical stored state rather than trusting it: an invalid position reads as unfeatured, and ties break deterministically on id.

**Studio.** A "Featured Order" action on each of the five collection list pages opens a dedicated screen (`/studio/content/{collection}/featured`) — not inline editing in the table, because featured order is a property of the *set*: moving one item renumbers its neighbours, and a control that only ever showed one row of that sequence is how two records end up claiming position 4. The screen offers search, status filter, add, remove, drag-and-drop (`@dnd-kit`, matching the Document Engine's existing pattern), and **Move Up / Move Down buttons as a first-class equivalent path, not a fallback** — every reorder is reachable by keyboard twice over, with an `aria-live` region announcing each move, add, and removal. Gated on `publish` (Admin/Head Admin), since featuring decides what a visitor sees first. The screen registers with Milestone 1's editor-state system, so an unsaved reorder inherits the navigation guard, sticky save bar, and unload protection with no bespoke logic.

**Public.** `getHomepage` no longer filters on a boolean and sorts by `referenceId` descending. Reference-ID order is a fact about when a record was created, not an editorial ranking — using it as one was exactly the hardcoded selection this milestone removes. Notes lost their `>= 5 substantive notes` gate, an editorial judgement the editor could neither see nor override. Existing eligibility gates (`isHomepageEligible`) and display caps are unchanged: this milestone replaced the *selection* mechanism only, per the brief, not the visual design.

**Migration.** Deliberately a no-op: `featuredOrder` is absent on every existing document and absence reads as `null`, so all content starts unfeatured and editors opt in explicitly. Nothing is inferred from publish date, creation date, or the old boolean. Confirmed against production: 0 records carry `featuredOrder`, while 2 still carry a legacy `featured: true` (one Build, one Blueprint) that nothing reads any more — see Deferred.

**Verified:** `tsc --noEmit` 0 errors, lint clean, **527/527 tests** (35 new: the ordering algebra including every rejection case the brief names — fractional, negative, `NaN`, duplicate — plus repository insertion/removal/reorder/renumbering/idempotence, and public ordering proving the homepage follows editorial order rather than reference-ID order), production build succeeds with all five new routes.

Live-verified in an authenticated Studio session, deliberately **without saving**, so no production record was written (confirmed afterwards: 0 `featuredOrder` values across all five collections). The Blueprints screen renders its empty state honestly; Feature moves an entry into the ordered list at position 1 and raises Milestone 1's shared save bar; adding three entries numbers them 1–3 with Move Up disabled on the first and Move Down on the last; Move Up on position 3 renumbers to a dense 1–2–3 with the displaced entry shifting down; Discard restores the empty state and clears the save bar.

**Deferred / not verified:** The **save path was not exercised against a database** — the pure ordering algebra and the write logic are unit-tested, but no end-to-end save was performed, because every candidate record is live production content and featuring one would change the public homepage. Two records still carry a stale `featured: true` that nothing reads; it was left in place rather than issuing a destructive `$unset` against production, and should be cleaned up in a maintenance pass. An editor can feature an entry that `isHomepageEligible` then silently rejects (missing hero, thin document), so it never appears — the reorder screen shows publish status but not eligibility, which is the most likely source of "I featured it and nothing happened". Ordering is not applied to collection index pages, only the homepage, because no index page currently ranks by featured state. Careers, Services, Engineering Profiles, Team, Users and Taxonomy are excluded by design, with the reasoning recorded in `lib/studio/featured-collections.ts`.

## Milestone 17 — Content Health Dashboard (v3.1 Milestone 3)

**What shipped:** An editorial health dashboard at the top of the Studio dashboard — a CI-style list of findings, not analytics. Architecture in three layers: `lib/studio/health/types.ts` (severity model), `rules.ts` (pure rules over a snapshot), `service.ts` (the single loader).

**The engine reports; it never decides.** Every rule delegates to logic that already exists: `homepageIneligibilityReason` for eligibility, `isValidFeaturedPosition`/`isFeatured` for ordering invariants, `FEATURED_COLLECTIONS.listEntries` for the entry+eligibility join, repository `list()` for status. No rule implements an editorial judgement of its own — a rule invented here would be a second source of truth, and the moment the two disagreed the dashboard would be lying about the site rather than describing it. `HealthIssue` makes `remedy` and `href` **required fields**, so the brief's "never a red warning without telling the editor how to fix it" is enforced by the type rather than by review.

**Severity is about public consequence**, not rarity: `critical` = something is wrong on the live site or a supposedly impossible invariant broke; `warning` = the site is intact but content is not doing its job; `info` = a standing fact, never a defect.

**Sections implemented:** Featured (duplicate positions, non-canonical/gapped numbering, invalid positions, featured-but-invisible), Homepage coverage (empty sections with qualifying content behind them), Review queue (awaiting review, approved-but-unpublished), Published-but-not-homepage-ready, Publishing counts, Recent activity, and Relationships (structure present, see Deferred).

Rules receive a snapshot and cannot fetch, so the N+1 the brief warns about is structurally impossible rather than merely avoided. The five orderable collections come through `FEATURED_COLLECTIONS`, so the Featured Order screen and the dashboard see byte-identical data and cannot disagree.

**A real bug the dashboard caught — in the dashboard's own dependencies.** On first render against production it reported 14 false criticals: "invalid featured position — stored position is undefined". Production documents predate `featuredOrder` and have the key *absent*, not `null`, and `undefined !== null` is true, so every `!== null` filter read a legacy record as "featured with an invalid position". ## Milestone 18 — Broken Relationship Finder (v3.1 Milestone 4)

**What shipped:** A full-graph integrity checker at `/studio/health/relationships`, and the real data behind Milestone 17's Relationships section, which until now reported zeroes.

**Graph integration — no second implementation.** `assertionsFrom` (the public repository's derivation of which record fields are relationships) was **exported** rather than reimplemented, and fed a different population: every record at every status instead of only the publicly visible ones. That difference is the entire point — the public layer resolves what it can and silently drops the rest, which is correct for rendering and useless for repair, because the dropped references are exactly the broken ones. **Health engine.** `relationship-health/rules.ts` classifies each assertion in one pass, first match wins, so one broken reference produces one actionable row rather than three describing the same mistake from different angles. **Performance.** Nine collections, one `list()` each, all in parallel, then every reference resolved against an in-memory index. A checker that looked up each target would issue one query per reference; relationship-dense content is precisely where that becomes thousands. A 300-entity/300-assertion scan is covered by test.

**UI.** A filterable list (collection, severity, relationship kind, free-text search over source and target titles) plus a live-region count. Each row is a single link — one tab stop per issue — landing on the editor that owns the broken reference, since the source record is the only place it can be repaired. Severity is rendered as a word, never colour alone.

The graph deliberately stores each edge once and derives inverses, so a genuine mutual relationship is two stored assertions and is *legal* — distinguishing an illegal cycle from a legal one needs a per-kind acyclicity declaration that does not exist yet, and inventing one would have created the editorial rule this milestone is forbidden from inventing. ## Milestone 19 — Global Studio Search (v3.1 Milestone 5)

**What shipped:** A dedicated search screen at `/studio/search`, plus the ranking, result model and collection coverage the existing search was missing.

**This was not a greenfield build, and treating it as one would have been the mistake.** The registry the brief describes — one adapter per collection, `registerSearchAdapter`, no collection-specific code in the engine, permission scoping per viewer — already existed from Phase 2 and powers the command palette. The genuine gaps were four:

1. **Ranking.** The old rule was "anything whose reference ID contains the query, then alphabetical", which ranked an unrelated entry above an exact title match whenever its reference ID happened to share the digits. `lib/search/ranking.ts` replaces it with explicit tiers — exact reference ID, exact title/slug, reference-ID prefix, title prefix, slug prefix, word prefix, substring — reference IDs leading because they are unique by construction, so an editor who types one has named exactly one record. Ties break on title then id, never on which adapter resolved first. Search here is navigation, not retrieval, so the tiers describe *how confidently a match identifies one record* rather than a relevance score nobody can predict.
2. **Collections.** Careers joined through the existing publishable factory (no new adapter logic). Taxonomy got the first adapter not built on that factory, because it has no workflow and no reference ID — reusing the publishable factory would have meant inventing a status for it; its `kind` becomes the subtitle, which is what makes two same-named entries distinguishable.
3. **Result model.** `SearchResult` gained `slug` (now matched and ranked, not just displayed) and `updatedAt` as an ISO string rather than a `Date`, because it crosses the server/client boundary.
4. **Per-keystroke database requests.** The palette debounces a request per keystroke. The new screen loads the viewer-scoped index once on the server and filters in memory, which is the right trade for a surface meant to be held open while narrowing a query.

**Keyboard:** arrow keys move the active result, Enter opens it, Escape clears. Groups are `<section>`s with `aria-labelledby`, and the result count is a polite live region.

**Verified:** `tsc --noEmit` 0 errors, lint clean, **589/589 tests** (16 new covering every tier including the exact-title-over-reference-ID-substring regression, tier ordering end to end, empty query, deterministic ordering for duplicate names verified by reversing the input, cross-collection ranking, hidden-status entries staying searchable, and grouping that preserves rank between groups), production build succeeds.

Live-verified against production: 105 entries indexed across every collection. `HZ-BP-005` returned exactly one result — "1 result across 1 collection" — grouped under Blueprints with reference-ID badge, status and relative update time. A broad `e` returned "96 results across 9 collections" with Taxonomy participating (`· technology` subtitles) and Engineering Profiles showing `EP-00x` identifiers, all filtering instantly with no network activity per keystroke.

**Deferred / not verified:** **Documents are not searchable.** They have no title, slug or reference ID — the only text they carry is the rendered body, which the brief explicitly excludes from indexing. Including them would have meant either indexing body content or inventing a synthetic title, so the honest outcome is that Documents remain reachable through their owning entry. **The command palette still queries per keystroke** and still uses its own fetch; it now shares the ranking module but not the snapshot, so the two agree on order while differing on transport. Unifying them is a follow-up, not a defect. **The whole index ships to the browser** — 105 entries is trivial, but this is linear in content volume and will need pagination or a server round trip at a few thousand entries. **Arrow-key and Enter navigation were not exercised in the browser** (typing and rendering were); they are covered by neither unit test nor manual check, which is the weakest part of this milestone's verification. ## Milestone 22 — Entry History Timeline (v3.1 Milestone 7)

**What shipped:** A read-only editorial activity timeline on all five content editors, built from what Studio actually records — and an explicit statement, in the UI, of what it does not.

**The finding that shaped the milestone.** The brief lists twelve event types and instructs: "If an event is not already represented by Studio, do not fabricate it." An audit of the data model found **no event log**. What exists is exactly three real sources: `createdAt` + `createdByUserId` (a creation event with an actor), `updatedAt` (the *most recent* save, with no actor and no earlier history), and `documentVersions` (genuine pre-overwrite snapshots with timestamps and actors — the only real *series* in the system).

The other nine — submitted, approved, rejected, published, unpublished, archived, restored, featured order changed, media replaced — leave no trace. `status` holds current state with no transition log; `reviewNote` holds the latest rejection reason with no timestamp or actor. Reconstructing them would mean inferring events from present-day state and inventing times and people. So they are **not** in the timeline, and the panel says so in plain text rather than leaving an editor to assume the absence means nothing happened.

**Event model.** `{ id, type, at, actor?, description, href? }`. `actor` is optional and never guessed: a save has no recorded actor, so it renders "actor not recorded" rather than attributing it to the creator, and a deleted user resolves to absent rather than a placeholder name. Sorting is newest-first with an id tiebreak, because identical timestamps are ordinary here (`createdAt` equals `updatedAt` until the first edit). Bucketing is by **calendar day**, not elapsed hours — "yesterday" means the previous date, which is what an editor means by it.

**Repository integration.** `loadEntryHistory` fetches the entry's documents, their snapshots in parallel, then resolves **every actor in one `$in` query**. The naive version looks up a user per event, which on an actively edited document is one query per snapshot — the N+1 the brief names. Derivation receives a synchronous lookup and cannot issue a query at all.

**UI.** One `EntryHistory` component, no per-collection variant. A real `<ol>` inside per-bucket `<section>`s with headings, so a screen reader hears an ordered list per date group; every row states who/what/when in text with no icon carrying meaning; timestamps use `<time dateTime>` and render absolutely rather than relatively, because a history is read to establish when something actually happened.

**Verified:** `tsc --noEmit` 0 errors, lint clean, **624/624 tests** (16 new: newest-first ordering, deterministic tiebreak on identical timestamps verified by reversing input, non-mutation, calendar-day bucketing including the 23-hours-ago-but-yesterday case and a future timestamp, grouping order and empty history, creation always present, no save event on a never-edited record, save carrying no invented actor, snapshot series with the oldest marked "started", unknown-actor resolution, and an explicit assertion that no workflow event types are emitted), production build succeeds.

Live-verified against production on the Work entry: four events rendering newest-first with strictly descending timestamps (20:49 → 20:38 → 20:13 → 15:25 UTC), grouped under "Earlier", showing "Entry created — by Rifaque", two real document-version events — by Rifaque, and "Metadata last saved — actor not recorded". Actor batching confirmed: one user resolved once and reused across three events.

**Deferred / not verified:** **Nine of the twelve requested event types are absent**, for the reason above. Closing that gap is a data-model change — an append-only event collection written by `createEntryTransitionAction`, `setFeaturedOrderAction` and the media fields — not a timeline change; the adapter shape here accommodates it as a new source rather than a redesign. **The browser checklist could not be completed**: verifying "review transition", "publish", "archive", "restore", "featured order change" and "document edit" appearing in the timeline requires those events to exist, and they do not; save/create/document-edit were verified from existing production data rather than by performing new writes. ## Milestone 23 — Editorial Event Log (v3.1 Milestone 8)

**What shipped:** The append-only event log Milestone 22 identified as the missing foundation, plus the rewiring of the timeline to read from it. Infrastructure, not a feature — no new screen.

**Events are facts.** `lib/events/repository.ts` exposes exactly four methods: `append`, `listForEntry`, `listForCollection`, `listRecent`. There is deliberately **no `update` and no `remove`** — append-only is enforced by the absence of an API to violate it rather than by a comment asking callers not to. A log whose rows can be edited is a record of what someone last claimed happened, not of what happened.

**Each event type owns its metadata.** `lib/events/schema.ts` defines a Zod **discriminated union**, not a shared `metadata: Record<string, unknown>` bag. A status change *must* carry `from`/`to`; a featured-order change *must* carry both positions; a media change *must* name its field. With a generic blob those are conventions that decay silently — a writer omits a field, nothing complains, and the gap is discovered by a reader long after the events are permanently written. Here both the type system and the parse refuse. Six types ship: `entry.created`, `entry.updated`, `entry.statusChanged` (with an optional `reviewNote`, present only on a rejection), `entry.featuredOrderChanged`, `entry.mediaChanged`, `document.updated`.

**No caller writes events.** `recordEditorialEvent` is called only from the **shared write paths** already in use — `createEntryCreateAction`, `createEntryUpdateAction`, `createEntryTransitionAction`, `setFeaturedOrderAction`, `createDocumentSaveAction`. That placement is the design: a collection joins the audit trail by using the factories it already uses, so a new collection cannot forget to log and no parallel mutation path exists to drift from. The actor is read from the session inside the recorder rather than threaded through five factory signatures, which would be five chances to pass the wrong one.

**Writes never fail the edit.** `append` validates, then swallows both validation and insert failures and returns `null`; `recordEditorialEvent` cannot throw. By the time either runs the entry is already saved, and turning a logging failure into a save failure would trade a missing row for lost work. `entry.updated` is paired with an `entry.statusChanged` when editing a published entry silently re-enters review, so the timeline can explain why something left the public site. `setFeaturedOrderAction` snapshots positions *before* the whole-set write and emits one event per entry that **actually moved** — a reorder that leaves an entry in place is not news, and logging it would bury the real changes.

**Indexes** are declared beside the schema (`entityType, entityId, createdAt` for the entry timeline; `createdAt` for recent activity; `actorUserId, createdAt` for per-person audit) and created lazily and idempotently from the first write, since this repository has no migration runner and connecting at import time would break the lazy-connection contract in `lib/db/mongodb.ts`.

**Timeline integration.** `loadEntryHistory` now loads recorded events first and, when any exist, renders **only** those — `fromRecordedEvents` maps each payload to its description ("In review → Published", "Featured position 1 → 3", "Removed from featured"). Derivation from `createdAt`/`updatedAt` survives strictly as a fallback for records that predate the log; without it every pre-existing entry would show an empty history, which reads as "nothing happened" rather than "not recorded". The panel says which case the reader is looking at. For any entry with recorded events, **no inferred events remain**.

`eventEntityTypeFor` moved from `record.ts` to `schema.ts` during verification: readers need it, and importing it from the writer pulled `auth()` — and so all of `next-auth` — into every consumer that only wanted to name an entity type.

**Verified:** `tsc --noEmit` 0 errors, **639/639 tests**. All six event types exercised against a scratch database (`hubzero_scratch`) through the real repository and the real `loadEntryHistory`: eight events written and all eight read back newest-first with strictly descending timestamps, each resolving to its true actor and rendering its own metadata — including the rejection note in `In review → Draft — "Needs a diagram."` and the `Featured at position 1` / `Featured position 1 → 3` distinction. A deliberately malformed `entry.statusChanged` (missing `from`/`to`) was **rejected at the boundary and not stored**. Recorded count equalled rendered count, confirming the derived fallback contributed nothing. Scratch collections emptied afterwards; production re-checked and unchanged, with no `editorialEvents` collection present.

**Deferred / not verified:** **The UI-driven half of the verification did not complete.** Events were verified through the real repository, schema and history service against the scratch database, but the browser harness stopped landing keystrokes and clicks partway through (typed text never reaching the field, a status transition and a featured-order click producing no write) and browser tooling then hit a rate limit. The wiring from each Server Action into `recordEditorialEvent` is therefore verified by code and by direct invocation, **not** by observing a Studio click produce a row. That check remains outstanding. `entry.mediaChanged` has **no producer**: the payload type exists and round-trips, but no write path emits it — media fields are saved as part of ordinary metadata updates and surface as `entry.updated`, so emitting it needs per-field diffing that does not exist yet. `document.updated` records the `role` but not `versionId`, so the timeline cannot yet link an event to the snapshot it produced. There is still no UI for `listForCollection` or `listRecent`; both exist for the activity feeds a later milestone will need.

## Milestone 24 — What's Changed? (v3.1 Milestone 9)

**What shipped:** `/studio/activity` — one chronological place to answer "what changed recently?", across every collection, built entirely on the Milestone 8 event log. No new tracking, no second store.

**The feed reads the log, and only the log.** Entity state is consulted for exactly one thing — turning an entry id into a title and a link — and never to decide *what happened*. An entry whose status is `published` today produces no "published" row unless a transition was actually recorded. This is why the page says so in its own description rather than leaving an editor to assume the feed is complete for pre-log entries.

**One describer, no UI switches.** The payload-to-prose mapping moved out of the history timeline into `lib/events/describe.ts`, which both surfaces now read. There is exactly one `switch` over the event union in the codebase. A new event type gets a timeline row, a feed row **and a filter checkbox** from one edit — the filter's labels are generated by calling the describer, not by a second list. A test asserts every type the schema declares is described, so a type added without a label fails the build rather than reaching the feed unlabelled.

**Filtering is server-side by construction.** The filter bar is a plain `<form method="get">` and therefore a Server Component with no client state: submitting navigates, the server reads the query string, and the database applies the filter. That is not a rule someone has to remember — there is no client-side path to filter through. It also means filters work without JavaScript and every filtered view is a shareable URL. Collections and event types are `<fieldset>`s with `<legend>`s, so a screen reader announces the group before the twelve checkboxes.

**Repository integration.** One new read method, `list(query, {limit, cursor})`, applying collection / event type / actor / date range **in the query**. Paging a filter applied in memory would silently return short pages as soon as the filtered set was sparser than the page size. The cursor carries `_id` alongside `createdAt` because timestamps are not unique — a single save writes several events in the same millisecond — and a timestamp-only cursor would skip or repeat the events sharing a boundary millisecond. `distinctActorIds` supplies the actor filter from the log rather than the user list, so the dropdown never offers someone who has never edited anything and whose selection would return nothing. `update`/`remove` are still absent, and the append-only guard test now pins the exact six-method surface.

**Search reuses the existing index.** Free text is applied by resolving *entries* through `listSearchIndex` and `matchTier` — the same ranking the search screen and command palette use — then filtering events by those ids. No event text is indexed. Reference-ID matching therefore keeps its punctuation-insensitive behaviour (`HZ-BP-701`, `bp701`) for free. The sharp edge is handled explicitly: an empty id list means "match nothing", never "no filter", or a search that found nothing would show the entire feed as though it had succeeded.

**Performance.** Three round trips per page regardless of page size: one indexed cursor query, one `$in` for every actor on the page, one search-index snapshot. Neither actor nor entry resolution is per-row — both are the N+1s this shape invites. Actor batching was extracted to `lib/studio/actors.ts` and is now shared with the entry timeline.

**Verified:** `tsc --noEmit` 0 errors, lint clean, **668/668 tests** (29 new: describer coverage of every schema type, filter parsing including unrecognised values, malformed dates and the inclusive upper bound, ordering, deleted entities, unknown and absent actors, actor batching, search translation including the empty-match case, filter forwarding, and cursor pass-through).

**Deferred / not verified:** **The feed is empty in production**, and will stay empty until events accumulate — the log has no producers running there yet, and Milestone 8's write paths have still not been observed writing a row from a Studio click. Nothing backfills history, by design. ## Milestone 25 — Review Flow Refresh (v3.1 Milestone 10)

**The reported symptom did not reproduce.** The brief describes workflow actions that succeed but leave the page stale until a manual refresh, with buttons stuck disabled forever. All six transitions were driven against a scratch database in **both** `next dev` and a **production build** (`next build && next start`), on the Blueprint detail page: draft → In review → Approved → Published → Archived → Restore, plus Reject with a note. Every one updated the status, swapped the button set and re-rendered the review panel within ~150ms–1.5s, with no manual refresh and no stuck controls. `StatusStepper` is the only component behind all six actions across all five content collections, and it already called `router.refresh()`.

One false lead is worth recording so it is not chased again: in the production build a **scripted** `element.click()` fires no request at all, which reads exactly like "the action does nothing". A real pointer click on the same button works. That is a harness artifact, not a product defect — an earlier milestone in this series made the same mistake in the other direction.

**What was actually wrong**, found while trying to reproduce the report:

1. **No duplicate-click protection.** Five rapid clicks on "Submit for review" dispatched **five** Server Actions. The first succeeded; the four that lost the race reported `"inReview" cannot move directly to "inReview"` — a raw internal message, shown over a transition that had in fact worked. The guard has to be a `useRef` written synchronously in the handler, not derived from `isPending` or component state: those flip on the *next* render, so every click in the same tick passes a state-based check.
2. **Blanket disabling with no progress.** Every workflow button disabled together and nothing indicated which action was running.
3. **No recovery guarantee.** `router.refresh()` was called inside the async transition with no error handling. A Server Action that rejects — a dropped connection, a 503 on the way out — left no error, no announcement and no defined path back to an enabled state. This is the closest thing found to the reported failure mode, and it is now impossible by construction rather than merely unobserved.

**Architecture — unchanged.** The server stays authoritative and no client state mirrors it. The only optimistic state is loading, exactly as the brief requires: the button reports that it is working, never that the transition has happened. Success still ends in one `router.refresh()`, and the page re-renders from fresh server data.

**Refresh model.** The action and the refetch are now separate concerns. The action's lifecycle is owned by a `try/catch/finally`, and the `finally` is the single reason the interface can never stay disabled — success, refusal and exception all release the controls. The refetch runs in its own `useTransition`, so `isRefreshing` keeps buttons unclickable for the brief window between "the server accepted" and "fresh props arrived", which is precisely when a stale button would otherwise be clickable. A refusal now also triggers a refresh: the server rejecting a transition usually means the entry moved on elsewhere, so the stale buttons that caused the refusal are resynchronised instead of left in place for another attempt.

**UI behaviour.** The button that was pressed shows "Working…" with `aria-busy`; the other transitions are blocked. That is a deliberate reading of "keep unrelated controls usable whenever safe" — every transition mutates the same `status`, so a second one is not an unrelated control, it is the race. Reject's **Cancel** is genuinely unrelated (it closes a local form and touches no server) and stays live throughout.

**Verified:** `tsc --noEmit` 0 errors, lint clean, **675/675 tests** (7 new, jsdom + Testing Library: success path refreshes exactly once, a five-click burst produces exactly one Server Action, progress label and `aria-busy` appear and are restored, a server refusal re-enables and resynchronises, a thrown action re-enables without claiming success, a fresh transition works after the previous settles, and Cancel stays usable while other transitions are blocked).

Browser re-verified after the fix: five rapid clicks on "Approve" produced **one** Server Action, **one** `entry.statusChanged` event and no error, where the same burst previously produced five and a spurious failure. The full chain Publish → Archive → Restore then ran cleanly. **This run also closed Milestone 8's open verification gap**: the four transitions written by real Studio clicks appeared as real `entry.statusChanged` rows with correct `from`/`to` in both the entry history panel and the `/studio/activity` feed, newest first — the first time the event log has been observed writing from actual UI use rather than from a direct call.

## Milestone 26 — Content Health: Entry Inspector (v3.1 Milestone 11)

**What shipped:** A collapsible health panel in all five content editors, showing publishing, featured, relationship, document, public-route and warning state for the entry being edited — without leaving it.

**This module owns no rules.** Not one verdict is computed in the inspector. Every finding it shows is produced by `loadHealthReport` — the same call, the same rules, the same severity and the same wording the global dashboard renders — and the inspector's entire job is to *select* the findings that name this entry and pair them with facts that entry already carries. A rule added to `health/rules.ts` appears in the panel untouched; a rule changed there changes here. There is no code path by which the two can disagree, because there is only one computation.

**Selection is by identity, not by text.** `HealthIssue.entity` gained an optional `id`, set once in `entityOf` — the helper every per-entry rule already used. Findings are matched by `entity.id === entryId` rather than by parsing an issue id or comparing labels. The valuable consequence is what it *excludes*: aggregate findings ("no Blueprints are featured", "the review queue is backing up") carry no entity at all, so they never leak into a single entry's panel. That is correct behaviour rather than a filter that happens to drop them — an editor cannot fix a collection-wide gap from one entry's screen.

**One request, no duplicated reads.** `loadHealthReport` already read every collection once and computed the relationship scan; it now *returns* the snapshot it used (`HealthReportWithSnapshot`) instead of discarding it. The inspector therefore gets the entry's status, featured position and homepage verdict out of the report rather than re-fetching the record, and gets relationship defects without a second integrity scan. The only additional reads are this entry's documents, issued concurrently with the report — two parallel loads, never a waterfall, and version lookups are skipped entirely for documents that do not exist.

**Reuse elsewhere is equally strict.** Homepage eligibility comes from `FEATURED_COLLECTIONS`, which already joins the public layer's own predicate — so the panel, the Featured Order screen and the dashboard cannot disagree about whether an entry would appear. Public routes are built through `publicRoute.entity`, never string-concatenated. Featured state goes through `isFeatured`, so the absent-vs-null normalisation holds here too. Documents come from the document engine's own repositories.

**UI.** A `<details>` panel, open by default and never a modal, with six sections: Publishing, Featured, Relationships, Documents, Public, Warnings. Every issue renders its `remedy` and a "Go to fix" link — both required fields on `HealthIssue`, so "never a red warning without telling the editor how to resolve it" is enforced by the engine rather than by this component remembering.

**Verified:** `tsc --noEmit` 0 errors, lint clean, **686/686 tests** (11 new: selection by entity id, exclusion of aggregate findings, pass-through of the *identical* issue object rather than a re-phrased copy, relationship defects the entry holds vs. ones pointing at it, missing vs. complete documents including that no version query is issued for a document that does not exist, public route construction and its absence for collections without a detail page, featured vs. unfeatured, and a null return for an entry absent from the snapshot).

## Milestone 27 — Featured Order as canonical editorial ordering (v3.1 Milestone 12)

**What shipped:** `featuredOrder` stopped being a homepage-only mechanism and became the editorial ranking every public collection page renders. The homepage now consumes the featured prefix of that same ordering.

**One ordering, expressed once.** `orderEditorially` was added beside `selectFeatured` in `lib/studio/featured-order.ts` and is defined *in terms of* it: featured entries first in editorial order, then everything else. The homepage's list is literally `selectFeatured` of the same input, which is the prefix of `orderEditorially` of that input — asserted by a test, so the two surfaces cannot drift into ranking differently. There is no second entry point and no `listHomepageFeatured`/`listCollectionFeatured` split.

**The remainder is not re-sorted.** Each collection already has a default order that means something — publication date for Notes, reference ID elsewhere — so `orderEditorially` layers editorial intent on top of whatever order it receives rather than deciding one itself. Callers sort first, then order editorially. That is what keeps this milestone from inventing a sorting rule while still making featured entries lead.

**Repository changes.** `listSummaries` orders *entities* before mapping, so every public collection page (`/work`, `/builds`, `/blueprints`, `/labs`, plus the notes index) inherits the ranking from one place — no page sorts for itself. `listNoteIndexEntries` keeps publication-date order and then applies the same two-step, carrying each entity's `featuredOrder` alongside because the note summary DTO does not expose it. `featuredEntities` (homepage) and the new `editoriallyOrdered` both read `featuredOrder` through one shared `orderable` helper, so the field is extracted in exactly one place. Types without `featuredOrder` are unaffected: nothing is featured, so the ordering is the identity.

**Studio wording.** The featured screens were re-framed from homepage-only to editorial ranking: page title "— editorial order", a description explaining that featured entries lead the collection page *and* that the highest-ranked eligible ones also fill the homepage section, and the list heading changed from "Featured — appears on {surface}" to "Featured — leads the collection". The all-ineligible warning now says the homepage section will render empty *while the entries still lead the collection page*, which was previously misleading. Eligibility, coverage warnings, drag-and-drop, Move up/down, the save flow and editor integration are untouched.

**Verified:** `tsc --noEmit` 0 errors, lint clean, **692/692 tests** (6 new: featured-first ordering, unfeatured entries keeping their incoming order, identity when nothing is featured, invalid stored positions falling to the remainder exactly as `selectFeatured` treats them, no entries lost, and the invariant that the ordering *begins with exactly what `selectFeatured` returns*).

**Deferred / not verified — read before merging:** **The browser verification in this brief was not completed.** Two things blocked it and both are worth knowing. First, the seeded fixtures never reached the public pages: five published Blueprints returned an empty `listSummaries`, because public visibility additionally requires a substantive case-study document, which the fixtures did not have — so the ordering was never exercised against real data. Second, and more seriously, the dev server started for this verification was reading **production** despite a `MONGODB_URI` override on the command line, which every previous milestone's server had honoured; it was killed as soon as its data was recognised as production, and production was re-checked and is unchanged (10 Blueprints, 1 Work, 1 Build, 1 Lab, 5 Users). Nothing was written to production. The consequence is that none of the brief's browser checks — featured entries leading each of the five collection pages, the homepage still using top featured entries, reordering changing both, featuring and unfeaturing moving an entry between sections — has been observed. The change is covered by unit tests at the ordering layer and is wired through a single call site, but it has not been seen working end to end on a page. **A verification pass with fixtures that pass the public visibility gate, on a server confirmed to be reading the scratch database, is required before this ships.** Pagination was not touched and not re-verified.

## Milestone 28 — Environment audit: why a scratch dev server served production data (v3.1 Milestone 13)

**The environment variable was never the problem.** `MONGODB_URI=<scratch> npx next dev` overrode correctly, and the process was connected to `hubzero_scratch` the entire time. This was proved on a single server: `/studio/content/blueprints` (uncached) rendered **only** the unique scratch marker record, while `/blueprints` (cached) on that same process rendered ten production Blueprints. One process cannot hold two Mongo connections here — `mongodb-source.ts` goes through the same `collections` → `getDb()` → `getMongoClient()` path as Studio — so the public page was not reading a database at all.

**Resolution chain.** `serverEnv()` (`lib/env.ts`) reads `process.env.MONGODB_URI` and nothing else; there is no dotenv call in application code. `next dev` loads `.env`/`.env.local` through `@next/env`, which assigns a parsed value **only when the key is not already present in `process.env`**. A command-line assignment is therefore authoritative, and `npm run dev` changes nothing — npm passes the environment through to `next dev` unmodified.

**Root cause: a cache key with no data-source identity.** `listPublicSummaries` wraps the repository in `unstable_cache` with the key `[PUBLIC_CACHE_VERSION, type, 'public-collection']` (`cacheKey` in `lib/public/queries.ts`). That key encodes a schema version but not *which database the bytes came from*. Next persists `unstable_cache` entries to `.next/cache/fetch-cache`, and every dev server started from this working directory shares that directory. The Studio instance running against production on port 3000 had already rendered `/blueprints`, writing production summaries under that key; the scratch server then read them back as its own.

**Confirmed by elimination**, not by inference: clearing `fetch-cache` alone did not change the already-running server (its in-memory entry survived), but a **fresh process with an emptied `fetch-cache`** rendered `/blueprints` with no production entries at all — correctly empty, since the lone scratch Blueprint lacks the substantive case-study document public visibility requires.

**Is it a Next.js bug?** No. This is documented `unstable_cache` behaviour given the key it was handed. It is a **project-level defect in development only**: in production each deployment has exactly one database, so the key is unambiguous there and no visitor can ever be served another database's content. In development it is a live footgun, and it is what silently invalidated Milestone 12's public verification — the ordering work was judged against production data on a server that was correctly pointed at scratch.

**Recommended fix (not applied):** include the resolved database name in `PUBLIC_CACHE_VERSION` or in `cacheKey`, so entries from different databases cannot collide. A `distDir` per environment would also work but is heavier and does not address the key itself. This was left unimplemented deliberately — the brief scoped this milestone to proving the implementation and explaining the environment, not to changing behaviour, and the change deserves its own verification rather than being appended to an audit.

**Deferred / not verified:** **Parts 3, 4 and 5 of the brief were not completed.** Public verification of featured-first ordering across `/blueprints`, `/builds`, `/work`, `/labs` and `/notes`, the homepage cross-check, Move Up/Move Down propagation, pagination across featured boundaries, and the regression sweep (eligibility, coverage warnings, featured dashboard, Entry Inspector) all remain outstanding. The blocker is now understood rather than mysterious: real publishable fixtures are required — a published entry alone is not publicly visible, it also needs a substantive document — and any such run must start from an emptied `.next/cache/fetch-cache` on a server with no production-connected sibling, or it will measure the wrong database again. Milestone 12's ordering change therefore still has **no** end-to-end public verification.

## Milestone 29 — Development cache isolation (v3.1 Milestone 14)

**Root cause (from Milestone 13).** `unstable_cache` keys encoded the schema contract (`PUBLIC_CACHE_VERSION`) but never the *dataset*. Entries persist to `.next/cache`, which every dev server started from the same working directory shares, so a server reading a scratch database would serve entries a production-connected server had written under the identical key.

**Cache design.** One prefix, `publicCacheScope()` = `${PUBLIC_CACHE_VERSION}:${databaseName}`, now leads every public cache key. Both halves must match for an entry to be reused: the schema contract *and* the database the bytes came from.

The database name is the right identifier because it is canonical and stable — it is the dataset's actual name, it is already what `getDb()` connects to, and it cannot vary between two requests of a process. It is deliberately **not** the connection string: a cache key can surface in file names and logs, so credentials must never travel there, and a test asserts the scope contains no user, password or host. The fallback for a missing or unparseable URI is a constant rather than a random value — a per-process random would silently disable the persistent cache, which is the failure mode this milestone must not introduce.

**Files changed.** `lib/public/cache.ts` (adds `publicCacheDatasetId`/`publicCacheScope`, memoised per module load) and `lib/public/queries.ts` (all six `unstable_cache` sites). Every `unstable_cache` call in the codebase lives in `queries.ts`, so the audit is complete rather than best-effort. One of the six — `getPublicHomepage`, keyed `['public-homepage', day]` — carried **no version prefix at all** and was the most exposed; it now carries the full scope. Caching is not removed, disabled or bypassed anywhere, and no unrelated key was churned.

**Browser verification.** Two dev servers run simultaneously from the same working directory with a shared `.next`: **Server A** on production (port 3010), **Server B** on `hubzero_scratch` (port 3011). `fetch-cache` was emptied first, then A's `/blueprints` was loaded *before* B's — the exact ordering that previously poisoned B. A rendered its 10 production Blueprints and did not contain the scratch marker. B then rendered **zero** production Blueprints and did not contain `Corporate-Editorial`; before this change, B rendered all ten. B's Studio showed only `Blueprint-ScratchOnly-Marker`, confirming B was genuinely connected to scratch and that its public page was reading its own dataset rather than a stale one.

**Verified:** `tsc --noEmit` 0 errors, lint clean, **698/698 tests** (6 new: two databases on one cluster producing different scopes, stability across calls so the persistent cache still works, no credentials or host in the scope, the schema version still carried, a constant non-random fallback, and a URI with no database distinguished from a named one).

**Performance.** No change to query counts, no cache disabled, no per-request busting. The scope is computed once per module load and reused. In production the key value changes exactly once, on the deploy that introduces it: existing entries are simply not found, are recomputed on first read, and age out — one cold pass, then identical behaviour. There is one database per deployment there, so this could never have caused a cross-database read in production; it closes a development hole only.

**Deferred / not verified:** Isolation is proven in the **negative** direction — B never shows A's data — which is the property that matters. The **positive** direction is only partly shown: B's public collection page rendered empty rather than rendering its own entry, because the seeded scratch Blueprint still did not clear the public visibility gate even with a real case-study document, so "public pages always show their own database" is evidenced for Studio but not yet for a populated public collection page. The brief's repeat-after-restart and repeat-after-deleting-`.next/cache` passes were **not** run, and the wider regression sweep (homepage, entry pages, metadata, sitemap, featured queries) was not re-exercised in the browser — the key change is uniform across all six sites and covered by unit tests, but only `/blueprints` was observed. A production build was not run in this milestone. **Featured Order's public verification (Milestone 12) still has not been repeated**, which was the point of unblocking this; it now needs fixtures that genuinely satisfy public visibility.

## Milestone 30 — Featured Order: public verification (v3.1 Milestone 15)

**Environment proven before anything else:** database `hubzero_scratch`, 5 Blueprints, known entry `Blueprint-Ord-Num4`. Production re-checked afterwards and unchanged (10 Blueprints, 1 Work, 1 Build, 1 Lab, 5 Users).

**What had been blocking every previous attempt.** Two earlier verification runs failed because the fixtures were not actually publicly visible, and the reason was never diagnosed — only worked around. It is now explicit. A Blueprint reaches a public collection page only when it clears **three** independent gates, not one:

1. `status: 'published'`;
2. a **substantive** `caseStudy` document — `hasSubstantiveDocument` requires **at least two non-heading blocks and at least 80 words**, so the single-paragraph fixtures used previously were rejected;
3. at least one **resolvable preview asset** — `previewAssetIds` must map to a media record with width, height, non-empty alt text and a genuine `res.cloudinary.com/.../upload/` URL, because `toPublicMedia` returns `undefined` otherwise and the summary is dropped.

Fixtures satisfying all three were built, and the entry additionally needs `shortDescription`, `liveDeploymentUrl` and at least one feature.

**Ordering verified.** Featured positions were assigned to deliberately disagree with creation order — fixture #4 at position 1, fixture #2 at position 2 — so a correct result cannot be a coincidence of insertion order. Both the repository and the rendered page returned:

`Blueprint-Ord-Num4, Blueprint-Ord-Num2, Blueprint-Ord-Num1, Blueprint-Ord-Num3, Blueprint-Ord-Num5`

Featured first in `featuredOrder` ascending, then the unfeatured entries in their existing order, all five present, none duplicated. The rendered `/blueprints` page matched the repository output exactly and contained no production entries, confirming the Milestone 14 cache isolation holds in the same run.

**Verified:** `tsc --noEmit` 0 errors, **698/698 tests**.

**Deferred / not verified — the majority of this brief.** Only `/blueprints` was verified. **`/work`, `/builds`, `/labs` and `/notes` were not**: each has its own visibility gate (Builds additionally require both `caseStudy` *and* `technical` documents, Notes require a `body` document, Labs require any document), and building four more fully-publishable fixture sets was not completed. **The homepage was not verified at all** — not the limits, not that its ordering is the prefix of the collection ordering, not that unfeaturing removes an entry from it. **No ordering operation was exercised**: Feature, Unfeature, Move Up, Move Down, drag-and-drop, Save, Discard and Reload were all untested in this milestone, so the claim that a reorder propagates to the collection page and homepage without a manual refresh remains unproven. **Pagination was not exercised**, honestly so: five fixtures cannot span a page boundary, and the brief explicitly forbids fabricating fixtures solely to satisfy it. **The regression sweep was not run** — Entry Inspector, Health Dashboard, Relationship Health, Editorial Activity, Search, Command Palette and the Featured Order editor were not re-opened after this change.

What *is* now established is the single most important claim, and the one that had defeated three previous attempts: on a real public collection page, backed by real fixtures, featured entries lead in editorial order and everything else follows unchanged.
