# Experience v3 — Progress Log

This is the canonical, in-repo record of what Experience v3 has actually shipped, milestone by milestone. It exists so a contributor — human or AI — with zero memory of prior sessions can read the repository and know the current stage, instead of relying on conversation history that doesn't persist.

**How to keep this current:** when a milestone completes, append a new `## Milestone N` section below in the same shape (What shipped / Why / Verified / Deferred). Do not rewrite prior entries except to correct a factual error — this is a log, not a living spec. If a milestone's decision is architecturally significant enough to need its own detailed rationale (the way v2.5's phases got individual `ADR_PHASE_N_*.md` files), write that ADR and link it from this entry instead of inlining it here.

**Branch:** `experience/v3`. As of Milestone 5, all work below is uncommitted in the working tree (`git status --short` shows the modified/new files directly — this log explains the *why* behind that diff, it doesn't replace reading it).

## Milestone 1 — Publishing Integrity

**What shipped:** Editing an already-`published` entry now requires `publish` capability (Admin/Head Admin only, via `requireEntryCapability`/`canEditEntry` in `lib/auth/permissions.ts`) and is forced back to `inReview` on save, clearing any stale `reviewNote`. Added a `reviewNote` field to the shared `PublishableEntity` model. Added a real reviewer **reject** path (`inReview → draft`) requiring a non-empty note, gated by `approve` capability (`canReject` in `lib/studio/workflow-permissions.ts`), surfaced as a Reject button + inline note field in `StatusStepper`.

**Why:** A prior repository audit found a published entry could be silently rewritten by its owner or any Admin with zero re-review gate, despite design docs claiming this gap was closed. This closed it for real, in code.

**Verified:** Typecheck/lint clean; 8 new tests directly covering `canEditEntry`/`canReject`. Not covered: full server-action integration tests (no `next/navigation`/`next/cache` mocking infra exists in this repo yet) and live Studio login flow (this repo's local `.env.local` points at a real database, so no test credentials were fabricated against it — see `docs/operations/ENGINEERING_BOOTSTRAP.md`'s working assumptions).

**Deferred:** No draft/live dual-copy versioning (an edited published entry disappears from public view until re-approved — a deliberate, stated trade-off, not a bug).

## Milestone 2 — Preview Integrity

**What shipped:** Real full-page preview via Next.js Draft Mode. `/api/preview` (enable — requires a real Studio session + `canActOnEntry`) and `/api/preview/exit` (disable). `lib/public/repository.ts`'s `findDetail`/`visible`/`mapSummary` gained a `bypassStatus`/`options.preview` path that bypasses only the *subject* entity's status gate — never propagated into relation/trace resolution. `lib/public/queries.ts` skips `unstable_cache` when previewing. A site-wide `PreviewBanner` renders whenever Draft Mode is active. The old in-Studio `BlockEditor` preview toggle (which rendered `BlockRenderer` — a Studio-only component — against unsaved in-memory blocks, and had falsely claimed to be "the same component tree" as the public site) is gone; its toolbar button now flushes autosave and opens the real Draft-Mode URL.

**Why:** `BlockRenderer` (Studio admin chrome) and `ProseRenderer` (public `.public-*` CSS) are, and always were, genuinely separate renderers. The old toggle's "what I see is what ships" guarantee was false. Draft Mode makes the guarantee true by construction — it's the same render path, not a resemblance of it.

**Verified:** Typecheck/lint clean; 429/429 tests passing (4 new tests for the bypass logic). Live-verified: real public pages unaffected, `/api/preview` correctly 401s unauthenticated. Not verified live: the full authenticated enable→preview→approve flow (same test-credential constraint as Milestone 1).

**Deferred:** `BlockRenderer`/`ProseRenderer` stay two separate components by deliberate architectural decision — see `PLANNING.md` §18/§26's Experience-v3 update notes. Not a gap; don't propose merging them without re-opening that decision explicitly.

## Milestone 8 — Interaction & Motion Polish

**What shipped:** A dedicated motion/interaction audit across all seven areas named by the brief (shared motion system, page transitions, founder experience, editorial motion, microinteractions, scroll experience, performance), using direct source reading plus one background investigation agent for the page-transition/scroll/viewport-entry questions specifically. The headline finding: the site's motion system was already unusually disciplined going in — `public-settle` (fade + ≤10px settle) already fires correctly on every cross-page navigation via each page's own `<main>` remounting, the persistent nav already never re-animates (it's a layout sibling of `{children}`, not inside it), zero viewport-entry/scroll-triggered animations exist anywhere (correct, per `DESIGN_SYSTEM.md`'s explicit prohibition), and zero spring/bounce easing exists anywhere. Two real, narrow fixes shipped: `Button.tsx`'s `disabled` state now transitions `opacity` instead of snapping instantly (it was missing from the transition-property list); `BlueprintFeatureList`'s mobile accordion dropped `margin-bottom`/`border-width` from its animated properties (down to `max-height`/`opacity`/`padding`), cutting two of five simultaneously-thrashing layout properties on a rare, mobile-only, low-element-count interaction.

**Why:** The brief asked for quality over quantity and explicitly warned against manufacturing motion to look productive. Given how much of the motion system had already been built correctly (partly from this same session's own Milestone 7, partly pre-existing), the honest, well-evidenced conclusion was that most workstreams needed verification and documentation of *why no change was needed*, not new animation — consistent with this project's repeated lesson this session that reading the real implementation before proposing a fix outperforms inferring gaps from a summary.

**Verified:** `tsc --noEmit` 0 errors, lint clean, 445/445 tests unchanged. Live-verified: the `public-settle` fade was caught mid-transition in a live screenshot on a real cross-page navigation, confirming it fires in practice, not just in code. Scroll-restoration was confirmed structurally sound by code (real server-rendered query params, no custom JS overriding native browser scroll restoration) but a live back-navigation spot-check was inconclusive due to test setup (the scroll position captured before navigating forward wasn't a deliberate, repeatable position) rather than any observed defect — reported honestly as unconfirmed rather than claimed either way.

**Deferred:** No `loading.tsx` exists for any public route — a real gap for perceived performance on a slow server response, but building matching skeleton states for 9+ route groups is new UI surface, not polish, and was judged out of scope for this pass. A shared-element exit transition for leaving a founder's profile (mirroring the existing About→profile entry) was considered and not built — there's no natural "return to this exact card" destination to morph into from the generic "Return to Engineering Profiles"/"How HubZero operates" footer links, so building one would require new scroll-to-card logic disproportionate to a polish pass; founder profile pages already benefit from the general page-transition system's exit/enter fade on top of the existing entry-specific continuity.

## Milestone 11 — Content Security Policy Validation

**What shipped:** Milestone 10's newly-added CSP (`script-src 'self'`, no exception) turned out to block Next.js App Router's own inline hydration scripts — confirmed live in a real browser before touching any code: a blank page and repeated `Error: Connection closed` exceptions from the React Server Components stream reader, the signature of `self.__next_f.push(...)`'s inline script calls being silently dropped by the browser. Investigated and tried the officially-documented, stricter fix first — a per-request nonce plus `'strict-dynamic'`, generated in `src/middleware.ts` and threaded through automatically by Next.js (confirmed by diffing the CSP header's nonce against the HTML's `nonce="..."` attributes — identical, with no explicit `headers()` call needed anywhere). It worked perfectly in `next dev` and for genuinely dynamic routes. It failed, empirically, for this app's statically-generated/ISR routes under `next start`: a page pre-rendered once at build/revalidation time ships with no nonce baked into its scripts at all (no request, no middleware, ever touches that render), while middleware still stamps a fresh, different nonce onto every subsequent request's CSP header — reproducing the identical blank-page failure, now scoped to every cached page instead of every page. Confirmed live via `x-nextjs-cache: HIT` on the broken response. Concluded that forcing full dynamic rendering site-wide to make the nonce match would be a disproportionate trade against the `revalidate = 86_400` ISR architecture two prior milestones (5 and 8) already verified as deliberate and correct, and reverted to the simpler, working answer: `'unsafe-inline'` for `script-src` (and, unchanged from Milestone 10, `style-src`), with every other directive kept at `default-src 'self'`-level strictness. `src/middleware.ts` was reverted to its original Studio-only scope in the process.

**Why:** A CSP that breaks the application it protects isn't a stricter policy, it's a broken one — and this project's own established discipline (verify empirically, don't trust the first thing that compiles) applied exactly here: the nonce approach *looked* correct, passed every dev-mode check, and only failed under a specific, easy-to-miss combination (production + a statically-cached route) that a dev-only verification pass would never surface.

**Verified:** `tsc --noEmit` 0 errors, lint clean, 446/446 tests unchanged, production build succeeds with all ISR `revalidate`/`expire` windows intact (confirmed directly from the build's route table, not assumed). Live-verified in both `next dev` and `next start` across every major public route plus Studio (authenticated and unauthenticated) — zero console errors on any, including real interactivity (search palette with live results, Contact form field entry) and the specific previously-broken cached-page scenario. One real regression caught and reverted before it could ship: the broadened middleware matcher tried during the nonce attempt made Auth.js set its CSRF/callback-url cookies on anonymous public page views, directly contradicting `/privacy`'s claim that a cookie is set only on Studio sign-in — confirmed via `curl` before and after the fix.

**Deferred:** `script-src`/`style-src`'s `'unsafe-inline'` is a disclosed, real reduction from the theoretical maximum, not a zero-risk default — compensating controls (DOMPurify sanitization of all authored rich-text content, Zod validation on every form input, Origin-header CSRF protection native to Next.js Server Actions) exist independently of CSP. Revisiting nonce-based CSP would require either abandoning this app's ISR architecture or Next.js's (currently experimental) Partial Prerendering maturing enough to reconcile static shells with per-request nonces — neither is in scope for a CSP-correctness milestone. No CSP-violation-reporting endpoint (`report-uri`/`report-to`) is configured, so a future regression here would only surface via manual testing, not telemetry.
