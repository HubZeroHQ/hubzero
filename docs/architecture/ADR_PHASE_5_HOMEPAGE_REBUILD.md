# ADR: Phase 5 (v2.5 Homepage Rebuild) found the homepage already well-composed, closed one real composition gap, and added a truthful opening statistic

**Status:** Accepted. Implemented across `Homepage.tsx`, `domain.ts`, `repository.ts`, and `page.tsx`.

**Context:** the HubZero Public v2.5 Engineering Architecture plan scoped Phase 5 as proving the homepage — "the reference composition of the entire public platform" — can be built from the primitives Phases 1–4 already established, plus implementing a truthful opening statistic. Unlike Phases 2 and 4, this audit did **not** find large blocks of hand-rolled markup duplicating an existing primitive. The homepage was already composing correctly in almost every place the brief asked about. This ADR records what the audit actually found: one real, narrow composition gap; one piece of fragile homepage-specific logic worth simplifying; and the live-statistic decision the brief required documenting either way.

## Audit: what already composes cleanly

- **`SectionHeader`** (not `DetailSectionHeading`) is used throughout, correctly — `EditorialPrimitives.tsx`'s own doc comment already documents this as the deliberate, more spacious variant for the homepage's rhythm, distinct from detail-page sections. No change needed.
- **`EditorialCard`** (`homepage/EditorialCard.tsx`) already composes from `EditorialPrimitives` (`MetadataRow`, `PublicationMetadata`, `RelationshipCard`, `TechnologyList`, `relationshipKey`) and `PublicImage`. It correctly does **not** use `RelationshipGroup`/`RelatedRecordsSection` — those assume a single subject with titled relationship groups; `EditorialCard` is a per-item card/row hybrid, a genuinely different shape. Forcing that reuse would fit content to a primitive it doesn't match, the same mistake the brief warns against in the other direction.
- **`AxisDiagram`** and **`EvidenceGraph`** (both platform primitives from Phases 2–3) are reused as-is for the Blueprint register, the Labs/Notes publication timeline, the Operating System pillars, and the Builds/Work featured-item graphs.
- **`ProfileHeroMedia`, `DetailGallery`, `RelatedRecordsSection`** were checked against the homepage's actual shape and don't apply: there's no optional single hero image block, no image gallery, and no single-subject grouped-relationship list anywhere on the homepage. Not reusing them here is the correct outcome of the audit, not an oversight — see Phase 4's ADR for the same reasoning applied to Engineering Profiles' evidence section, which *did* have a real match.

## Audit finding: `EvidenceGraphFocusSync` was reusable here and wasn't wired up

Phase 3's ADR stated Homepage's `RelationshipGraph`/`EvidenceGraph` call sites weren't wrapped in `EvidenceGraphFocusSync` because "the adjacent markup there is an `EditorialCard` grid keyed by `feature.entity.url`, not a `relationshipKey`-keyed `RelationshipCard` list, so there is no matching id on the other side." **Re-reading `EditorialCard.tsx` during this phase's audit shows that claim was already inaccurate at the time it was written**, not just outdated: `EditorialCard` renders `RelationshipCard` for every relationship on a feature, and `RelationshipCard` has carried `data-evidence-node={relationshipKey(relationship)}` unconditionally since the same Phase 3 change that added it — including inside `EditorialCard`. The `feature.entity.url` key Phase 3's ADR pointed to is the outer grid's React `key` (for `EditorialCard` instances), a separate concern from the `data-evidence-node` id carried by each relationship *within* a card.

Concretely: the Builds section's `EvidenceGraph` renders `builds[0].relationships`, and `builds[0]`'s own `EditorialCard` (the first card in the grid directly below it) renders `RelationshipCard`s for that exact same array — both sides already carry matching `data-evidence-node` ids. The same is true for the Work section (`work[0]`, and today `work` is always a single-item array). This phase wraps both sections' graph-and-grid in `EvidenceGraphFocusSync`, reused byte-for-byte unchanged from Phase 3, and adds a test (`Homepage.test.tsx`) proving the shared id appears exactly three times per relationship — once on the graph's edge, once on its node, once on the matching `RelationshipCard` — confirming the pairing is real, not just plausible.

This correction doesn't require editing `ADR_PHASE_3_EVIDENCE_GRAPH.md` itself — historical ADRs are left as the record of what was decided and why at the time; this note is where the correction belongs.

## Homepage-specific cleanup: the `#evidence` anchor id

The Hero's "Inspect the evidence" link jumps to `#evidence`, which must land on whichever of Builds/Work/Blueprint/Labs-and-Notes actually renders first — each is independently conditional on real data. Before this phase, each section re-derived "am I first?" with a growing chain of negated-sibling-length checks (`id={!builds.length && !work.length && !blueprint ? 'evidence' : undefined}`, and so on). This is exactly the kind of homepage-specific logic duplication the audit was asked to find: correct today, but a latent bug for whoever adds a fifth conditional section without noticing every existing chain needs a new `&&` clause. Replaced with one `firstEvidenceSection` value computed once, that every section's `id` prop compares itself against. This stays a local `const` inside `Homepage.tsx` — homepage-specific control flow, not a candidate for extraction anywhere else, per the brief's explicit instruction not to invent reusable primitives for homepage-only ideas.

## The live statistic

The brief asked for a truthful opening statistic and, if the data model can't support "the originally proposed" one, the closest truthful metric instead, documented. The audit found: `PublicHomepageProjection`'s `work`/`builds`/`labs`/`notes`/`profiles` arrays are **capped, curated subsets** for display (`.slice(0, 1)`, `.slice(0, 2)`, a `featured` flag filter, and similar) — `projection.builds.length` is not "how many Builds exist," it's "how many fit in the featured slot" (today, always ≤ 2, regardless of the real count). Using any of those lengths as a headline number would be exactly the vanity/invented metric the brief prohibits — it wouldn't grow as the site grows, and a reader could trivially notice it never changes.

**What's actually true and cheap:** `getHomepage()` already calls `source.listEntities(type)` for all six evidence-bearing types (Work, Build, Blueprint, Lab, Note, Engineering Profile) to build those featured arrays. `listEntities` filters to `status: 'published'` at the query level (`mongodb-source.ts`), so the *un-sliced* array lengths are already a true published-record count, and they're already being fetched — no new query. `PublicHomepageProjection` gained one new field, `publishedRecordCount: number`, computed as the sum of those six lengths inside `getHomepage()`. It intentionally does not factor in `PUBLIC_ENTITY_ROUTES` (the presentation-layer feature-flag gating everything else in `Homepage.tsx` already respects) — a record's published state is a data-layer fact, independent of whether its section is currently toggled on for navigation. All six flags are `true` today, so this has no visible effect now, but the choice is deliberate and worth remembering if that ever changes.

It renders as the first entry in the Hero's existing `home-hero-register` fact box (`Published — N public record(s)`), not as new visual chrome — that register already existed, already had three purely textual rows (Source/Standard/Structure), and already carries the aria-label "HubZero publication principles." Adding a fourth, numeric, real row is composition, not new infrastructure. The register's decorative `"Public record / 001"` eyebrow (an exhibit/reference-number convention, matching the site's `HZ-XXX`-style IDs used elsewhere) was deliberately left untouched — it isn't a numeric claim about live data, and conflating it with the real count would be the opposite of this phase's "truth over aesthetics" instruction.

## Performance audit

- **Bundle impact:** `EvidenceGraphFocusSync` was already shipped to the client wherever `EvidenceGraph` renders `Homepage`'s barrel import (`../evidence-graph`) already pulled in both; this phase's new import doesn't add new client code, it activates a client component that was already reachable and already tested. No new dependency, no new client boundary type — the brief's "reuse `EvidenceGraphFocusSync` unchanged" is exactly what happened.
- **Image loading:** unchanged — `EditorialCard` already sets `priority` only for the first prominent card per section; no new images were introduced.
- **Streaming:** the homepage today is one Server Component tree rendered from a single `getPublicHomepage()` call in `page.tsx`, with no `Suspense` boundaries. Splitting data-fetching into per-section streams would be a genuine performance opportunity, but it is new data-fetching infrastructure (multiple parallel queries, loading states, Suspense boundaries), not composition from what exists — outside this phase's "minimal new infrastructure" mandate. Recorded here as a real, identified opportunity for a future phase to pick up deliberately, not implemented now.
- **Server/client boundary:** unchanged shape — `Homepage` and every function inside it stay Server Components; `EvidenceGraphFocusSync` remains the only client boundary anywhere on the page, exactly as before this phase.

## Validation

- `npx vitest run` — 59 files / 377 tests passing (7 new: the opening-statistic singular/plural rendering, the `#evidence` anchor landing on the correct section across three scenarios including a "more than one section present" case proving exactly one `id="evidence"` ever renders, and the `data-evidence-node` triple-match proving the new `EvidenceGraphFocusSync` wrapping is real).
- `npx tsc --noEmit` — clean.
- `npx eslint .` — clean.
- `npx prettier --check` — clean on every file this phase touched.
- **Accessibility:** no ARIA attributes changed; `EvidenceGraphFocusSync`'s wrapper `<div>` carries none of its own (confirmed in Phase 3), so it's transparent to the accessibility tree. The new Hero statistic is a plain `<dt>`/`<dd>` pair inside the register's existing `<dl>`, which already had an `aria-label`.
- **Reduced motion:** no new animation was introduced; the hover-highlight CSS the new `EvidenceGraphFocusSync` wrapping activates on the homepage is the same rule set already covered by the global `prefers-reduced-motion` rule since Phase 3.
- **Manifesto compliance:** no bespoke visual language was introduced — the statistic uses the Hero's existing register styling, and the evidence-graph pairing uses existing, unmodified CSS from Phase 3.
- **Duplicate composition:** none found remaining after this phase — the one real gap (`EvidenceGraphFocusSync` non-adoption) is closed; the one fragile-logic pattern (`#evidence` anchor derivation) is simplified; everything else already composed correctly before this phase touched it.
- Not run: `next build` / a live browser check, for the same `.env.local`-points-at-production reason recorded in Phases 1–4.

## Self-review

- **Does this homepage feel composed rather than handcrafted?** Yes, and this audit is the first phase where that was already mostly true going in — the main finding was a gap in applying an existing primitive, not a pile of hand-rolled markup to replace.
- **Did we reuse existing platform primitives?** Yes — `EvidenceGraphFocusSync` reused unchanged, closing a real gap; `SectionHeader`/`AxisDiagram`/`EvidenceGraph`/`EditorialCard`/`EditorialPrimitives` all confirmed already correctly in use.
- **Did we avoid homepage-specific infrastructure?** Yes — `firstEvidenceSection` is a local `const`, not an exported helper; `publishedRecordCount` is a data-layer field, not a UI component.
- **Does the homepage tell one coherent story?** The narrative order and copy are unchanged by this phase; the one addition (the opening statistic) reinforces the existing "evidence before claims" framing already present in the same register.
- **Would another engineer understand this composition immediately?** Yes — the diff is legible as "wrap two existing sections in an existing component" plus "add one real field," not a new pattern to learn.
- **Did we accidentally duplicate anything that already exists elsewhere?** No — the opposite: this phase removed a duplicated-logic pattern (the anchor-id chain) and corrected a prior phase's inaccurate claim rather than repeating it.

## Note on the external architecture plan

Per this phase's own instruction: if an audit repeatedly disproves an assumption in the Engineering Architecture plan, that plan should be corrected after merge rather than forcing future phases to keep following it. This is now the third phase in a row (2, 4, 5) whose audit found the plan's specific predictions — named primitives, in Phases 2 and 4; a claimed non-reuse reason, in this phase — didn't match the real code. That planning document isn't tracked in this repository (see `hubzero-v25-phase-brief-vs-real-code` project memory), so it can't be corrected here; this ADR is the durable, in-repo record of the correction for whoever plans Phase 6 onward.
